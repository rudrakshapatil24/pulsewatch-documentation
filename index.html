PulseWatch: Early Health Outbreak Detection & Alerts

CodeAstra 2.0 | Syntory Pulse Lab | Domain: Web & Product Development | Problem statement: Health Outbreak Detection & Alert System

Team: Syntory | Leader: Soham Mayekar

Live demo: https://syntorypulsewatch.netlify.app/

All data in this prototype is SIMULATED sample data. It is a demonstration of the workflow and the explainable risk logic. It is not real public-health intelligence and must not be used for health decisions.

1. Overview and problem statement

Official outbreak reports in India, such as IDSP weekly district summaries, arrive late. Clinic counts, news reports, search trends and weather data sit in separate systems, so small clusters are often noticed only after they spread. Simple threshold alerts give a number but no reason, and frequent false alarms teach people to ignore them.

PulseWatch shows an early-warning approach for districts. It combines four signals into a per-district risk level of Normal, Watch or Alert, compares each district with its own historical baseline, and explains every alert in plain language. Officers can acknowledge, resolve and review alerts.

2. Objectives

  • Combine several weak signals into one transparent district risk score.
  • Make every alert explainable: reasons, baseline comparison, contributing sources, confidence, and a suggested next step.
  • Keep a human in the loop: officers review and record verdicts.
  • Run fully offline with no paid services, API keys or backend.
  • Be honest about what is simulated, what is implemented, and what is future scope.

4. Technology stack

  • Frontend: React 18.3, Vite 5, Tailwind CSS 3, Recharts 2
  • Detection engine: plain JavaScript (ES modules), no ML libraries
  • Tests: Node.js built-in test runner (node --test)
  • Browser smoke test: Playwright-core (optional, see section 12)
  • Data: static JSON files generated by a seeded script

5. Architecture

+--------------------------------------------------------------+
| 1. DATA (SIMULATED)   data/*.json                            |
|    districts | clinicCounts | newsSignals | searchTrends |   |
|    weather   (produced by scripts/generateSampleData.js)     |
+------------------------------+-------------------------------+
                               | imported as plain objects
+------------------------------v-------------------------------+
| 2. DETECTION ENGINE (pure JS, no UI, unit-tested)           |
|    normalize.js  -> 0-100 indices from baseline ratios       |
|    score.js      -> weighted score, thresholds, guard rule   |
|    explain.js    -> plain-language reasons and confidence    |
|    alerts.js     -> open -> acknowledged -> resolved         |
+------------------------------+-------------------------------+
                               | function calls at load time
+------------------------------v-------------------------------+
| 3. UI (React + Vite)                                         |
|    src/data.js   loads data, runs engine once per district   |
|    src/store.jsx in-memory state (alerts, reviews) via reducer|
|    src/pages/*   Dashboard, Map, Districts, Alerts,          |
|                  Analytics, Review, Method                   |
+------------------------------+-------------------------------+
                               | officer verdicts (in memory)
+------------------------------v-------------------------------+
| 4. FEEDBACK LOG   recorded verdicts only; not used to retune |
+--------------------------------------------------------------+

How components communicate. There is no network layer. src/data.js imports the JSON files and the engine, then builds one assessment per district. React components read that data and dispatch actions to a reducer in src/store.jsx. The reducer calls the engine's alert transition function, so invalid moves (for example, resolving twice) are rejected in one place. Nothing leaves the browser, so no secrets or API keys are needed.

6. System workflow: Collect → Detect → Explain → Alert → Improve

Stage Prototype behaviour Real-world intent (not built)
Collect Loads seeded sample files Pull clinic returns, news, search and weather daily
Detect Converts each signal to an index against the district baseline Same, with validated thresholds
Explain Writes reasons, baseline comparison and confidence Same, with source links
Alert Creates Watch or Alert records, which officers manage Send to officers first, then to the public after approval
Improve Records officer verdicts in a log Use verdicts to tune thresholds, with audit trail

8. Installation and running

Requirements: Node.js 18 or later (tested on Node 22), npm.

cd pulsewatch
npm install            # installs React, Vite, Tailwind, Recharts
npm run data           # optional: regenerate the seeded sample data
npm test               # run the 7 unit tests
npm run dev            # start the app at http://localhost:5173

For a production build:

npm run build && npm run preview     # serves the build at http://localhost:4173

No environment variables, API keys or external services are required.

The generator creates 12 districts across 7 states. Five districts have scripted profiles: two outbreak surges, three moderate rises. The rest show normal activity. Each run with seed 2026 produces identical files.

10. Risk-scoring methodology

This is a transparent rule-based score. It is not a trained machine-learning model, and its weights and calibration points have not been validated against outbreak history.

Step 1: baseline. The baseline for a signal is the average of the 8 weeks before the current week. The ratio is the current week divided by that baseline.

Step 2: indices (0 to 100). Each signal is converted using a fixed scale:

Signal Weight Index rule Calibration point
Clinic cases 0.40 (ratio − 1) / 2.5 × 100, floored at 0 3× baseline → 80
News reports 0.20 count / 4 × 100, capped at 100 2 reports → 50
Search trend 0.20 (ratio − 1) × 100, floored at 0 1.6× baseline → 60
Weather 0.20 rainfall mm × 70 / 120, capped at 100 120 mm in 3 days → 70

Step 3: weighted score. score = round(0.40·clinic + 0.20·news + 0.20·search + 0.20·weather)

Step 4: level. Normal below 40, Watch from 40 to 69, Alert at 70 or above.

Step 5: guard rule. A source contributes if its index is 40 or more. If the level would be Alert but fewer than two sources contribute, the level is capped at Watch and the reason is shown.

Worked example (also used in the unit tests):

Signal Index Weight Contribution
Clinic 80 0.40 32.0
News 50 0.20 10.0
Search 60 0.20 12.0
Weather 70 0.20 14.0
Total 68 → Watch

Limitations of the method. A single source can contribute at most 40 points (clinic at 100 × 0.40), so with these weights the guard rule rarely changes an outcome. It is a safety net that becomes meaningful only if weights change. The unit tests exercise it with custom weights. The sample data results are: Mumbai Suburban 83 (Alert), Bengaluru Urban 74 (Alert), Chennai 49 (Watch), Pune 43 (Watch), Ahmedabad 36 (Normal, just below the Watch threshold).

11. API endpoints

There is no HTTP API. The engine runs in the browser as plain functions. If a backend is added later, the natural endpoints would be GET /districts, GET /alerts, POST /alerts/{id}/transition and POST /reviews. None of these exist today.

12. Testing

Unit tests (npm test): 7 tests cover the worked example, threshold boundaries (39/40/69/70), the guard rule with custom weights, the normalisation calibration points, the baseline ratio, the alert lifecycle including invalid transitions, and an end-to-end assessment and explanation for a surge profile. Result on the last run: 7 pass, 0 fail.

Browser smoke test (npm run e2e, requires npm run preview running on port 4173 and a Chromium binary): loads every page, checks navigation, map selection, district search and filters, acknowledge and resolve flows, officer review submission, analytics rendering, mobile layout overflow, and console errors. Result on the last run: 20 of 20 checks pass. Set CHROME_PATH to a Chromium binary and install playwright-core if you want to run it.

Manual checks: the dashboard and map were reviewed in screenshots at 1366 px width. Label collisions on the map were found and fixed during this review.

Not tested: real data quality, performance with thousands of districts, accessibility beyond basic keyboard use of map markers, and any browser other than Chromium.

13. Privacy, security and ethics

  • No patient data. The design uses district-level aggregated counts only. The sample data contains no personal information.
  • No secrets. There are no API keys, tokens or environment variables. Nothing is sent to a server.
  • Simulated labels. Every data panel carries a SIMULATED label, and every data file sets meta.simulated.
  • Human review. The product intent is that officers review alerts before any public message is sent. The prototype only records their verdicts.
  • Alarm fatigue. The guard rule and explanation requirements aim to reduce false alarms. This has not been measured.
  • Regulation. Any real deployment would need review against the Digital Personal Data Protection Act, 2023, and guidance from national public-health authorities before use.
  • Not medical advice. Suggested next actions are generic operational prompts for discussion, not clinical guidance.

  3. Add email, SMS and web push alerts that are sent only after officer approval.

15. Demonstrating to judges

  1. Open the dashboard. Point out the SIMULATED notice and the data-source labels. Say that every number is sample data.
  2. Go to Districts. Select Mumbai Suburban. Walk through the score table: clinic 83 × 0.40 = 33.2, news 100 × 0.20 = 20.0, search 76 × 0.20 = 15.2, weather 72 × 0.20 = 14.4, total 82.8, shown as 83.
  3. Go to Alerts. Show the reasons, the baseline comparison ("135 this week vs about 44 typical") and the confidence label. Acknowledge one alert, then resolve it, and show the history entry.
  4. Go to Officer Review. Submit a "False alarm" verdict with a note. Show the review log.
  5. Go to Method & Sources. Show the worked example (score 68, Watch) and the limitations list. Stating the limitations openly is the strongest answer to "does this work on real data?"
  6. Resize to a phone width to show the responsive layout.
  7. Click "Reset demo data" to restore the seeded state between runs.

16. Known limitations (summary)

  • All data is simulated. There are no live integrations.
  • The score is rule-based and its weights are not validated. It is not a machine-learning model.
  • The guard rule rarely changes outcomes with the current weights.
  • Officer verdicts do not change thresholds.
  • Alerts and reviews are in memory and reset on page reload.
  • The map is a schematic layout, not a geographic map. Two districts are nudged for legibility.
  • No authentication, roles or audit trail.
  • Tested on Chromium only.
